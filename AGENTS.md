# Working on Koharu

Koharu is a local-first manga translator: a Rust workspace with a TypeScript interface, shipped as a desktop app. This file holds durable decision rules only. Architecture, file layouts, crate and helper names, model inventories, commands, and anything else a refactor can change belong in crate READMEs and the docs. Normal Rust, TypeScript, testing, formatting, and Git practices are assumed.

## Booharu

This repository is Booharu, a personal Windows fork of Koharu. The rules below are upstream's and still apply; this section is the fork's own and wins where the two differ.

- The goal: add a multi-page chapter, press one button, and get a very passable scanlation (clean, translated, lettered) with no further input. Hand edits stay possible afterwards and always win over automatic choices. Every feature must also work on its own for someone who never uses the automatic run.
- Booharu stays on Koharu as its base. Koharu releases are merged from upstream's real history into `main`, the fork's copy of Koharu, and then from `main` into `booharu`. Where Koharu and Booharu fix or build the same thing, keep Koharu's, and put back on it only what Koharu's lacks. Booharu 0.0.5 is built on Koharu 0.95.2: its release commit, `81ee36aa`, which brings 0.94.1, 0.95.0 and 0.95.1 with it, was merged from upstream's history straight into `release/booharu-0.0.5` (`dfecf08e`), as 0.85.6's, 0.86.0's, 0.89.0's, 0.90.0's, 0.92.0's and 0.94.0's (`ce51f553`, which brought 0.93.0) were, not through `main`, so it's the next release's merge base. Each Koharu release merges from its own release commit. A file both sides changed takes Koharu's side with each `Booharu:` line put back, where Koharu now does that work if it moved (as the inpaint stage's run filters now wrap Koharu's `write::ops`, see What runs leave alone); `crates/koharu/tauri.conf.json`, `tauri.linux.conf.json` and `tauri.macos.conf.json`, as JSON takes no comments, keep Booharu's product name, identifier, window title and `createUpdaterArtifacts: false` unmarked; and Cargo.lock takes Koharu's versions, with the new workspace version for Booharu's crates. Then the Koharu version Booharu names moves to the new one: `PREVIEW_INSTALL.md`'s line saying what 0.0.5 is built on, its `.khr` range while koharu-scene's format stays the same, and the comments over the cache keys in `.github/workflows/booharu-check.yml` and `preview-windows.yml`, whose keys keep their 0.85 names so the warm caches still serve. About's "Based on Koharu" reads the version Tauri reports, the workspace's, so it follows by itself; look at About to confirm it. What the 0.95.2 merge brought, dropped and leaves is under The Koharu 0.95.2 merge, what the 0.94.0 merge leaves under Limits of the Koharu 0.94.0 merge, what the 0.90.0 and 0.92.0 merges left under Limits of the Koharu 0.90.0 and 0.92.0 merges, and what the 0.89.0 merge left under Limits of the Koharu 0.89.0 merge.
- Keep edits to upstream files small and Booharu's own code in modules of its own, so the next Koharu release applies with few conflicts. An edit to an upstream file is a hook call or a mount line where it can be, and carries a comment starting with `Booharu:` (`/// Booharu:` on a field), so a search for `Booharu:` lists every touch point. Keep upstream signatures: add a setter or an optional field, never change a constructor such as `Tools::new`, and upstream's tests and examples compile untouched.

- Commands: Koharu 0.90.0 took out `lib/backend.ts`, and runs every command as a TanStack query or mutation, whose cache shows a failure as one error toast (`lib/queries.ts`); nothing imports `@/lib/backend`. A command whose answer nothing waits on goes through Koharu's `send()`. Booharu code that awaits a command's answer outside a query or a mutation runs it through `call()` (`lib/booharu/call.ts`), a keyless mutation, so a failure shows as that one toast and the promise rejects with it as an `Error`; once the command settles, `call()` lets go of the mutation, whose gcTime is 0, so the cache drops it and its answer on the next timer turn (a 0 ms timeout) rather than keeping every answer for the session. Koharu 0.94.0's own `send()` (547c291c, tested by `tests/lib/queries.test.ts`) lets each mutation go the same way once it settles, and its client defaults (b43358da) run every query and mutation in TanStack's `always` network mode, so a command runs while the browser reports being offline, as when the computer's Wi-Fi drops: each goes to the desktop's own backend, never the internet. Booharu keeps `tests/booharu/offline.test.tsx`, as Koharu has no test of that mode. Inside a `queryFn` or a `mutationFn` a command runs directly (`commands.x(...)`), never through `call()` or a helper built on it, which would toast the failure twice: so a mutation saving a Booharu section calls `writeBooharuSection`, the queued write with no toast of its own, and other code `saveBooharuSection`, the same write through `call()`, both in turn through `queueBooharuWrite`. A read Booharu keeps quiet on purpose, one the view shows its own way or one that only adds to what Koharu shows, as the boxes' lettering and text effects, the fonts' local names, the models Analyze chapter and Explain use, the first-start note, the Context tab's series, chapter and term usage, and the pages' levels status and preview, carries `meta: { booharuQuiet: true }`, which `unlessQuiet` (`lib/booharu/quiet.ts`), on the query cache's marked line in `lib/queries.ts`, keeps Koharu's query cache from toasting; a failed mutation always toasts. `refreshPreferences` reads Koharu's settings again once no save of them is under way. New interface code never brings `@/lib/backend` back: it sends a command through `send()`, awaits one through `call()`, or runs it directly inside a `queryFn` or a `mutationFn`; it marks a read it keeps quiet; it types a key it holds `ParseKeys` (see Interface); and it adds a key as options on Koharu's hotkeys (see Keys), never a key path of its own.

- Settings: one `koharu_config::Section` per area in `booharu-core`, a `[booharu-<area>]` table in `~/.booharu/config.toml` and a field of `BooharuPreferences`, which `booharu_get_preferences` and `booharu_save_preferences` read and save whole; the agent's `booharu_set_settings` changes one section through `BooharuPreferences::save_section`, which saves it alone, a table in it only in the keys named, a key it held set to null removing it. Defaults live in Rust with `#[serde(default)]`, and only overrides are written. A value a caller gives that doesn't read is refused and never saved, so a save never writes a value that wouldn't read back; a stored value that doesn't read reads as its default, as Koharu's own settings have since Koharu 0.87 (`koharu_config` drops the key its error names, a whole list, or a whole map keyed by category, for one bad entry in it, and reads the whole section as its defaults when it can't tell which key), and stays in the file until a save changes it. Koharu's write edits a table in the file key by key and refuses, naming nothing, a save that wouldn't read back as set, as a change to a map still holding a bad entry, or to a table whose every value is bad, would be; for Booharu's sections koharu-config's glue module writes such a key whole instead, as it read, with the change, over what was edited by hand, while Koharu's own sections keep Koharu's refusal. Only a settings file that can't be read, such as one that isn't TOML or UTF-8, or no home folder, is an error. Booharu's tests read a stored value as the app reads it, through koharu-config's two marked hooks for them: `booharu_read_section`, which reads a section from a settings file's text, as booharu-core's `testing::stored` and `unreadable` and the desktop's MCP and K tool tests call it, and `booharu_update_file`, which saves a change to a settings file at a path as `update` saves `config.toml`, as `testing::saved` calls it. Model output and project files still fail closed. Secrets go only through `koharu_config::secrets`. - Borders: koharu-scene's `TextStyle.stroke_method` (`StrokeMethod`), a paragraph key left out of the file while unset, says how a text's borders draw. No method is `expansion`, Koharu's border, each letter grown on its own under every fill, as Koharu 0.89.0 draws it but with no holes beside a dot (below). It's the default so that a text with no method, Koharu's or Booharu's, looks as it does in Koharu, and a Booharu text left at it stays readable there; Koharu 0.89.0's stroke keeps the border of a dot wound against its letter, which its earlier growth lost (koharu-rs #1073, #1292), and Booharu's region keeps it too. `contour` is the choice beside it: one border grown around the letters merged, every run with that border together, so a translucent border shows no darker overlap where letters touch, and no border shows through a see-through letter. `text/contour.rs` makes both methods' regions. The outline method, in the type bar's More border options (`BorderExtras`), lists Expansion first and writes null for it and `contour` for Contour; Reset writes null; the fx tag's `outline_method` names a method unlike the lettering default's; PSD export writes either as Photoshop's Outside stroke. Booharu 0.0.4 kept a method only in `.khrproj` projects, which 0.0.5 can't open, so no value it stored changes meaning; 0.0.5's earlier development builds read no method as Contour, which no release wrote, so it gets no upgrade (see Changes). koharu-renderer's `text/draw.rs` draws both in Koharu's passes, through its marked lines: without Contour regions, every run's second border (`Pass::Outer`) under every run's border (`Pass::Stroke`) under every fill (`Pass::Fill`); with them, the regions filled non-zero under the fill pass alone. Its `bold()` and `turn()` are shared with `text/contour.rs` and `booharu/paint.rs`, and `bold()` with `booharu/lines.rs` too. Koharu 0.89.0 draws a border pass as the glyphs filled and stroked, with round joins, twice as wide as the pass grows them, by synthetic bold's growth and the border's width, and the second border's width too in `Pass::Outer`; but where the stroke's half-width passes a small contour, as beside the dot of an i or a colon once a border is wider than about a fifth of the text size, the stroke folds back past it and the non-zero fill leaves arrow-shaped holes beside the dot, as Koharu 0.89.0 draws them too. So a Booharu border pass fills its run's region instead, non-zero, in the pass's paint, with no stroke and no layer: the run's glyph outlines, unhinted at its size and variation and not emboldened, merged non-zero and grown with round joins by the pass's growth before they're turned and placed, as glifo strokes a glyph in its own space, in the text's own coordinates under `draw`'s transform. That's what the fill and the stroke cover together wherever the stroke doesn't fold, and one shape, so a translucent paint shows one even alpha with no layer; a pass that grows by nothing draws as Koharu's does. ## Product

- Models run on the user's machine. Pages and text leave it only through a hosted provider the user chose.
- Editor behavior that is not already specified matches Photoshop or Clip Studio Paint. Ordinary editing happens in the app, not through an export and re-import round trip.
- Desktop API keys and sign-in tokens are stored encrypted, with the key kept in the OS credential store. Do not fall back to a project environment file.

## Changes

- Never add backward compatibility, except that a project file a release wrote keeps opening. When an API, schema, file format, configuration, or ownership boundary changes, delete the replaced form: no alias, forwarding layer, compatibility parser, upgrade decoder, stub, or disabled flag.
- Changing a released project format ships an upgrade to the new one, which leaves the file as it was if it fails. A format no release wrote gets no upgrade.
- Prefer a coherent ownership redesign over cosmetic renaming. Defaults and provider-specific behavior belong to the component that owns them, not to a central list of special cases.
- Make the smallest change that solves the problem. Leave unrelated configuration, documentation, generated files, and workflows alone. A feature does not land beside drive-by cleanup.
- When two changes implement the same workflow, keep one and extend the existing command or configuration.
- If the code you are changing has moved, rebase onto its new owner. Do not port a patch onto a deleted tree.
- Invalid configuration and model output fail closed. A project file fails to open only when it doesn't parse, isn't this app's format or version, or would crash a reader; its structure is kept by the operations that write it, not checked again. Do not add a repair or defaulting layer that can change meaning.

## Code

- Write the smallest code that does the job. Inline a helper with one caller, keep a small module in its parent, and do not wrap a type without adding a responsibility.
- Reach for a crate before writing code: a well-known external crate first, then one in this repository. Hand-write only what no crate covers, and prefer a cross-platform crate to per-platform branches.
- Keep safe public APIs apart from unsafe FFI, dynamic loading, and build integration.
- Do not hand-edit generated or derived source. Change its input and rerun the generator.
- Comments explain ownership, invariants, upstream mapping, or a deliberate divergence. Do not narrate straightforward code.
- Do not commit credentials, model weights, datasets, generated outputs, or machine-specific files.
- Search with `rg`, never `grep`.

## Interface

- User-visible strings go through the translation function and the locale files. Hardcoded English in a translated surface is incomplete.
- An interface language's display name is that language's own name in every locale.
- The translation-target language list stays in the active UI language. Drop a country name unless the entry is a real variant.
- Do not show status the current selection already implies. Do not add a second job kind, cancel path, or counter for an operation an existing command covers.
- Use the existing control library for standard interaction. Commit on selection or an uncanceled drop, never on focus or hover. Ignore a canceled drag. A shortcut never steals keys from a focused control.

## Models

- A port stays structurally traceable to a commit-pinned upstream implementation. Preserve checkpoint-affecting names, construction order, parameter paths, tensor layouts, execution order, and postprocessing semantics. Explain each intentional divergence next to the affected code.
- Missing or unexpected weights mean an architecture or parameter-name mismatch. Fix that before changing the loader.
- Every model has the same public lifecycle, with model-specific inputs and outputs. Network and weight loading stay apart from preprocessing, postprocessing, slicing, and result types. Do not add pass-through types or layers.
- Accept a device at the model boundary and convert it once. Create token IDs and index tensors on the model device; a CPU tensor used against accelerator embeddings is a defect.
- Use the established loading paths unless they are proven insufficient.
- Disable gradient tracking during inference.

## Performance

- Optimize and benchmark on the actual target device with representative inputs. Load assets and warm models outside the measured region, and account for asynchronous accelerator execution.
- Remove redundant transfers, synchronization, allocations, and per-pixel host loops before adding concurrency or caching.
- Report the device, input size, baseline, result, and correctness difference.

## Verification

- Run the smallest relevant check or focused test once, in the debug profile. Run full suites, other profiles, or end-to-end tests only when asked.
- Add a test only where it protects a real regression boundary. Do not lock a translated phrase, a language display name, a registration string, or a one-line behavior the owner can read. Do not add a second harness for behavior existing tests cover, a test of a compatibility shim, or a benchmark nobody asked for.
- A model port needs a structured comparison with upstream on identical inputs: shapes, ranges, boxes, scores, masks, and ordering. A green build is not that comparison.
- A UI change needs a screenshot of the affected state. For truncation, include a long label.
- A green check is not acceptance.
