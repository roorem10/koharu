# Working on Koharu

Koharu is a local-first manga translator: a Rust workspace with a TypeScript interface, shipped as a desktop app. This file holds durable decision rules only. Architecture, file layouts, crate and helper names, model inventories, commands, and anything else a refactor can change belong in crate READMEs and the docs. Normal Rust, TypeScript, testing, formatting, and Git practices are assumed.

## Booharu

This repository is Booharu, a personal Windows fork of Koharu. The rules below are upstream's and still apply; this section is the fork's own and wins where the two differ.

- The goal: add a multi-page chapter, press one button, and get a very passable scanlation (clean, translated, lettered) with no further input. Hand edits stay possible afterwards and always win over automatic choices. Every feature must also work on its own for someone who never uses the automatic run.
- Booharu stays on Koharu as its base. Koharu releases are merged from upstream's real history into `main`, the fork's copy of Koharu, and then from `main` into `booharu`. Where Koharu and Booharu fix the same thing, keep Koharu's fix.
- Keep edits to upstream files small and Booharu's own code in modules of its own, so the next Koharu release applies with few conflicts. An edit to an upstream file is a hook call or a mount line where it can be, and carries a comment starting with `Booharu:` (`/// Booharu:` on a field), so a search for `Booharu:` lists every touch point. Keep upstream signatures: add a setter or an optional field, never change a constructor such as `Tools::new`, and upstream's tests and examples compile untouched.
- Rust: `crates/booharu-core` holds what Koharu's pipeline hooks call (settings types, the attribute registry, shared types) and depends only on koharu-scene, koharu-config and light crates, never on koharu-pipeline, koharu-agent or koharu-desktop. `crates/booharu` holds feature logic and may depend on `booharu-core`, koharu-pipeline, koharu-scene, koharu-llm and koharu-renderer; koharu-pipeline never depends on it. A Koharu crate that calls Booharu code, or holds some of its own, gets one glue module, `booharu`: `src/booharu.rs` in koharu-pipeline, koharu-canvas and koharu-renderer, where it reads the fonts' names in other languages from the faces `fonts/catalog.rs` has on disk, `src/booharu/` in koharu-desktop, and `src/tools/booharu/` in koharu-agent, declared in `tools.rs`; koharu-pipeline's scheduler keeps the run policy in a second one, `src/scheduler/booharu.rs`, which reaches its private fields. No crate per feature.
- Canvas: Booharu's koharu-canvas code lives in its `src/booharu.rs`. Koharu's canvas enums gain only `Tool::OcrBox`, the O tool, and `Effect::Booharu`, whose `booharu::Effect` carries what a Booharu gesture did to the host, with `Gesture::Booharu` inside the crate; a later Booharu gesture goes in under these, never as another Koharu variant. Booharu's canvas settings are one `BooharuSettings`, set by `Canvas::set_booharu`: for now the T tool's text defaults, the default font and colours, and a drawn box's starting fit, Best, so its text grows with the box. The desktop pushes it at startup, to each canvas it makes, and after each save that can change it: `booharu_save_preferences`, the agent's settings saves, and Koharu's `save_preferences`, for the Preferred fonts. A later canvas setting goes into it.
- Interface: components in `packages/koharu/components/booharu/<area>/`, hooks and logic in `lib/booharu/`, tests in `tests/booharu/`, styles in `app/booharu.css`, which `app/layout.tsx` imports after `globals.css`; upstream components get one mount line each. Strings go in `public/locales/<lng>/booharu.json`, merged over `translation.json`, as `booharu.<area>.<key>`, `history.steps.<label>` for an edit label, or `tools.<tool>` for a Booharu tool's name, where Koharu's tool rail looks it up. Each change adds all 12 languages, with each language's own plural forms, and leaves `translation.json` as Koharu ships it. A language's file may also override a Koharu key at Koharu's own path, only in that language and only where its text must differ, such as to say Booharu or to add a plural form Koharu's file lacks; an override never copies Koharu's text. Koharu's `FontPicker` takes Booharu's optional props, the favourites, Favorites only and local names, which `useBooharuFontPicker` gives and each mount spreads, and `noneLabel`, a leading row standing for no family; its arrow keys and Enter are built in. A command that writes one setting on its own, such as a font's star through `booharu_set_font_favorite`, runs in turn with the interface's section saves through `queueBooharuWrite`, so none of those saves puts back the value it read before; the agent's `booharu_set_settings` saves only the section it changes, in one read and write under the settings file's lock, so it never undoes either.
- Names: crates `booharu-*`, modules `booharu`, desktop commands and agent tools `booharu_<verb>_<noun>`, edit labels `booharu_<action>`.
- Settings: one `koharu_config::Section` per area in `booharu-core`, a `[booharu-<area>]` table in `~/.booharu/config.toml` and a field of `BooharuPreferences`, which `booharu_get_preferences` and `booharu_save_preferences` read and save whole; the agent's `booharu_set_settings` changes one section through `BooharuPreferences::save_section`, which saves it alone, a table in it only in the keys named, a key it held set to null removing it. Defaults live in Rust with `#[serde(default)]`, and only overrides are written. A bad value fails closed: it is refused, never saved, and a bad stored value is an error, never replaced by its default. Secrets go only through `koharu_config::secrets`. Never a second copy of an upstream setting, never a field in upstream's `Preferences`, and no migration of older settings. `[booharu-lettering]` holds the default text look, `default` {fill, stroke, stroke_width} and `detect_colors`, and the lettering categories' `auto` (Pick fonts automatically, off), `categories` ({family, bold, italic} for each category given its own font, with no blank family and no entry setting nothing; none to start with), `small_text` (0.012, above 0 and at most 1) and `model_confidence` (0.6, from 0 to 1), and `[booharu-fonts]` the font picker's `favorites`; the default font is no Booharu setting but the first of Koharu's Preferred fonts. `[booharu-runs]` holds the Run menu's `presets`, each a `name` and its `stages`, which set the menu's stage switches and start nothing, the run policy, `retries` (0 to 5), `on_page_failure` (`continue` or `stop`) and `order` (`pages` or `stages`), and `finish_sound`. Settings join Koharu's tabs by topic: the text look, the lettering categories and Apply under Typesetting, colour detection under Pipeline; `openSettingsSection` takes a link to a section, opening Settings first from the editor. A topic of Booharu's own gets a tab after Koharu's, listed in `booharuTabs` (`lib/booharu/settingsLink.ts`) and `components/booharu/settings/BooharuTabs.tsx`, with its name at `settings.tabs.<tab>` in `booharu.json`: Runs, for `[booharu-runs]`.
- Booharu-only data on a scene layer goes in its attributes under the `booharu` namespace, each key a type in the registry `booharu_core::attrs`; data the renderer must read becomes a real scene field. The keys are `lettering` {category id, source: user or model, confidence from 0 to 1} on a block, `auto` {origin, source, text, style} (the hand-edit record), `qc_ok` [check id or `glossary:<term>`], `flags` [{kind, message}], `read_note` and `review_note` (text), `sfx_subtitle` {block}, `original_scan` (true) and `skew` {x, y} in degrees. Write them only with the registry's ops inside the action's one edit, leaving locked layers out and saying how many; a reader takes a bad value for absent.
- Box tools: each box action builds its one edit in `crates/booharu`'s `boxes` module, which the desktop commands and the agent tools share, as koharu-agent can't call koharu-desktop. The interface defines each per-box action once, with its label, when the selection enables it and what it calls, in `lib/booharu/boxActions.ts`, the one list the Story row menu, the Edit menu, Box details and later the canvas's right-click menu show; Box details shows the sections listed in `components/booharu/details/sections.tsx`, each for the texts its `shows` takes, and opens on one when an action names it. A later action or section is one more entry. A reviewer's note is the `review_note` attribute on a block or a text layer, set or cleared by one `booharu_set_review_note` edit; a locked layer refuses it, as Koharu refuses attribute writes there. The Detection stage marks each block it makes with Koharu's `c2pa.detection` attribute, and a block made by hand, such as with the O tool, is made with no `c2pa` attribute, so a block without `c2pa.detection` is hand-made.
- Hand edits: `booharu.auto` records what Booharu's automatic steps wrote, in the same edit as the write: the Recognition hook the hash of each source it reads, the Translation hook, on every translation it writes, the hash of the text and the style values it left, and Apply and a change of category the style they wrote. Hashes are stable short hashes of the trimmed text, never Rust's `DefaultHasher`. `booharu_core::edited` tells which parts were changed by hand: the source or the text, when its hash differs, or with no record when no `c2pa` action wrote it; the style, when a recorded key differs, a span carries a mark for one, or the record's origin is `agent`, as after the agent's Apply; and drawn, a block without `c2pa.detection`. Text typed by hand has no record, so it counts as hand-made. Apply, and any later automatic step that changes text already made, leaves hand-edited blocks alone unless told to include them; a later stage's automatic write records its own keys in `auto` too.
- Default text look: new text with no family of its own gets a copy of the first Preferred font, so finished pages keep theirs when the list changes: every translation a run writes, a first translation typed by hand and the T tool's text; with no Preferred font, none is written. With `detect_colors` on, Booharu writes no colours, so the colours Koharu measured, or copied from the source for a typed translation, stay; off, the default colours replace them, except that a sound effect keeps Koharu's legibility outline when the default sets none. The T tool's text always gets the default colours. Booharu restyles translations already made only through Apply (`booharu_apply_text_style`), one edit that never recolours with detection on, and, while `auto` is on, a change of category, which changes only their font.
- Lettering categories: `booharu_core::lettering` holds the 18 `LetteringCategory` ids in Settings' order, 0.0.4's fifteen (`normal_dialogue` to `menacing`) then `handwritten`, `sign` and `electronic_voice`; the interface lists them in `lib/booharu/categories.ts`, which doesn't compile without each, and names them at `booharu.lettering.categories.<id>`. A category's font (`LetteringSettings::category_font`) is its own entry, else Normal Dialogue's, else none, which keeps the default look's font; an entry without a family takes Normal Dialogue's family, else a copy of the default font. It sets only a translation's `style.chars` `family`, `weight` (700 or null) and `italic` (true or null), never other keys nor marks, so word styles survive it. A block's category (`effective`; only blocks have one, so the T tool's text gets none) is, with its reason: a user's label (`user`); a model's label of a presentation category, `title`, `phone_text`, `sfx`, `handwritten`, `sign` or `electronic_voice`, at any confidence (`model`); `sfx` for Koharu's sound effect, `Role::Sfx` (`sfx`); a model's label of a delivery category, `thoughts`, `weak_shout`, `moan`, `whisper`, `shy`, `crying`, `menacing` or `shout`, at least `model_confidence` sure, none counting as sure (`model`); `small_text` when its glyphs, the size detection measured on its source, else 0.0.4's estimate from its frame and wording, are under `small_text` of the page's height, never without either (`small_text`); its balloon's shape, round `normal_dialogue`, rectangle `narration_box`, spiky `shout` (`shape`); else `floating` (`floating`). A model's label of another category never wins. `booharu_core::shape` classifies an outline as 0.0.4's `bubble_shape.rs` did, over kurbo paths flattened and simplified at 0.1% of their length: spiky with at least 5 dips deeper than 8% of the smallest rotated rectangle's short side and a solidity under 0.90, else a rectangle with a rectangularity of at least 0.90, else round. A block's balloon is the one holding it, else the smallest on its page whose outline holds its source's centre, as for a box drawn by hand; the shape is worked out when asked, never stored. Booharu's own steps write a category font only while `auto` is on, and with it off write the look above and nothing more: `styles::new_translation` gives it in place of the default font to a run's translation, whose record counts its keys as automatic, and to one typed in Story, through the agent or on the canvas, each through `lettering::auto_category`; Apply gives it to each translation, keeping those keys' marks; and a change of category gives it.
- Changing a category: `booharu::lettering::set_category` builds one edit labelled `booharu_set_lettering_category` for any number of blocks, which the desktop command `booharu_set_lettering_category` (the user's choice, `None` for Automatic) and the agent's tool of that name (a model's) share: each block's new label, or none for Automatic, and while `auto` is on its translation's new category's font with its record, built even when the label stays, so picking a category again applies a font changed since; one that changes nothing adds no undo step. A user's choice restyles a font changed by hand, and its Automatic clears any label; a model's never replaces a user's label nor restyles a block whose style was changed by hand, and its Automatic clears only a model's label. Locked blocks are left out and counted, and it answers `changed`, `locked`, `kept_user_label`, `kept_hand_edited` and `untranslated`. `booharu_get_lettering` answers each block of a page: its category, reason, label, balloon shape with its measures (rectangularity, solidity, spikes), and whether it was changed by hand. The agent's label tool refuses the four categories a label never gives, `normal_dialogue`, `floating`, `small_text` and `narration_box`; `booharu_get_text_styles` (read-only) answers the look, each category's resolved font with where it comes from, and blocks' categories; and `booharu_apply_text_style` takes a `category` or a `shape` to letter every block as, whether `auto` is on or not, recorded with origin `agent`. In the interface, Settings > Typesetting's Lettering categories card (`components/booharu/lettering/`) has the switch, a searchable category picker, the chosen category's font, whose leading row, "Same as Normal Dialogue" or for Normal Dialogue "Same as the default font", removes its own family but keeps its own bold and italic, with bold and italic, which give a category without an entry one of its own with no family, so it still follows Normal Dialogue's, the categories with their own font, Suggest fonts, which fills only categories without one from 0.0.4's starting list (NFKC, without spaces, ignoring case, catalog fonts counting as available) and gives the three new ones none, and Apply. Per box, the Story row's category tag, a Layers block row's second line, Box details' Lettering section and the `category` box action, Change category, show it, read through `booharu_get_lettering` per page under Story's query key so each change reads it again; their pickers offer Automatic and the 18, and say while `auto` is off that fonts follow categories only with it on.
- Pipeline hooks: `Pipeline::run` puts the run's snapshot of Booharu's settings in `PipelineConfig.booharu`, never saved, whichever way the run was queued, and the stages read only that. Its `runs`, the run policy from `[booharu-runs]`, is set only there, so the Run button's, the agent's and MCP's runs all follow it; `None`, as `PipelineConfig::default()` holds it, is Koharu's own behaviour, which only a run made without `Pipeline::run`, as in the scheduler's tests, keeps. A section the snapshot can't read refuses the run, as it refuses a typed translation's edit, and the canvas keeps the settings it had. The Translation stage's `written()` adds the look and the record after placement's op, and the Recognition stage adds the record beside its source write, each through koharu-pipeline's `booharu` module.
- Run policy: a stage task's failure carries a class, read in `stages::run()` from the error chain before it's worded: Invalid (`Error::Invalid`, or an edit the project refused), Write (any other scene error, which ends the run whatever the policy), Load (a model that couldn't load, which another try with nothing freed can't help), HostedRetried (a hosted 429 or 5xx, which koharu-llm already sent again) and Retryable (anything else: a dropped connection, the time limit, a broken, blank or short answer, a model's own error, a panic). Only Retryable is tried again, after 2, 5, then 10 seconds (`retry_wait`), holding no page in flight and no GPU turn meanwhile, and Stop ends the wait; each retry sends `Retrying`. A failed recognition batch is none of its pages' own: each page is read again alone, after its wait when it's tried again, or at once with no try counted when it wouldn't be (a refused edit, no tries left), so only a page that fails alone is given up on or stops the run. With `continue`, a page out of tries is given up on: its waiting jobs leave the graph, an edge from the translation before it to the one after keeps the conversation in page order, `PageFailed` is sent, a stage already running on it may still write, and the run ends `DoneWithProblems`, listing the failures; with `stop`, it ends `Failed`, as Koharu's first failure does. `order = stages`, for runs over pages only, hands out only the earliest stage left, unloading every model as the run is admitted, a stage's model as its last job leaves, and at the end all but what another queued run needs. `Queued` carries the run's `stages` and `pages` (true for a Project or Pages target), and Koharu's `wait` tool names the new events through `booharu::WAIT`. A hosted translation request, any vendor's but Koharu's own model, has ten minutes to answer through `crate::booharu::answered`, around each request in `turn.rs`, never on koharu-llm's shared client, and then fails as Retryable.
- Carrying on: `booharu::runs` plans what each page still needs from the `c2pa` records Koharu's stages leave on its blocks, as its module doc sets out (a scanned page with no blocks needs every stage, unless a panel, balloon or block there carries detection's record), and groups the pages that need the same stages, ordered by their first page. `booharu_run`, the desktop command and the agent tool alike through `booharu::runs::carry_on` and a `RunHost`, queues the groups with every stage on as ordinary runs, one after another: the next once a run ends Done or DoneWithProblems, while a run that fails or stops, a Stop pressed once a run has ended (which `Pipeline::stops` counts), or the project closing, ends the group. A group's follower is spawned on the thread that queues its first run and frees the group's place however it goes, so a caller that went away meanwhile can't leave a group no one follows. One group goes at a time, a call while it goes answers it, and each run it queues is announced as `booharu_run_group` {group, run, index, count}. With fewer stages it queues one ordinary run, as Koharu does; with nothing left it answers no run, and the interface offers Run all stages again. As a scanned page detection found nothing at all on, or one that fails every try, is planned again each time, the agent's tool tells it to stop at a new plan whose every page has the stages it had in the plan before, and to name those pages, rather than loop. The Run button goes through it with every stage on, over pages or the project. In the interface, `lib/booharu/jobs.ts` keeps each job's record after Koharu's fold, from which the Activity center lists a run's failed pages and Retry failed pages queues one ordinary run per set of stages its pages need: from the stage each failed at through the run's later stages, with any earlier stage of the run the page never finished and its failed stage doesn't wait for in Koharu's run graph, which the run dropped as it gave the page up; a job shows only in the project it was queued in. `lib/booharu/chime.ts` chimes as a run over pages ends, unless it stopped, and once for a carrying-on group; its `finished()` is where a later batch takes those chimes.
- `booharu` is the accepted work and the base for every branch. `main` is a clean copy of upstream and is never developed on. Branches are named `wo-NN-topic`, `fix/topic`, `chore/topic` or `release/booharu-X.Y.Z`.
- Work reaches `booharu` only after it compiles, passes the "Booharu check" workflow, and has been tested by the owner in a Windows build. Releases are tagged `booharu-vX.Y.Z`; the version lives in `FORK_VERSION`. Windows is the only platform for now.
- New non-trivial logic leaves one small test. A change report ends with what was skipped or not checked, and any risk.
- Every user action that reads or changes the open project gets its `booharu_` agent tool in the same change, with accurate read-only annotations; the in-app agent and the MCP server share one toolset, so both offer it. `booharu_get_settings` and `booharu_set_settings` cover every Booharu settings section, so a new section needs no tool of its own; `booharu-mcp` is read-only over MCP.
- Credit the owner only as `roorem10`, with the GitHub noreply address. No real names or personal email in commits, pull requests, issues or files.
- Booharu's own commits may name an AI co-author. Anything sent to upstream Koharu follows the Contributing rules below.

## Product

- Models run on the user's machine. Pages and text leave it only through a hosted provider the user chose.
- Editor behavior that is not already specified matches Photoshop or Clip Studio Paint. Ordinary editing happens in the app, not through an export and re-import round trip.
- Desktop API keys and sign-in tokens are stored encrypted, with the key kept in the OS credential store. Do not fall back to a project environment file.

## Changes

- Never add backward compatibility, except that a project file a release wrote keeps opening. When an API, schema, file format, configuration, or ownership boundary changes, delete the replaced form: no alias, forwarding layer, compatibility parser, upgrade decoder, stub, or disabled flag.
- Changing a released project format ships an upgrade to the new one, which leaves the file as it was if it fails. A format no release wrote gets no upgrade.
- Prefer a coherent ownership redesign over cosmetic renaming. Defaults and provider-specific behavior belong to the component that owns them, not to a central list of special cases.
- Make the smallest change that solves the problem. Leave unrelated configuration, documentation, generated files, and workflows alone. A feature does not land beside drive-by cleanup.
- When two changes implement the same workflow, keep one and extend the existing command or configuration.
- If the code you are changing has moved, rebase onto its new owner. Do not port a patch onto a deleted tree.
- Invalid configuration and model output fail closed. A project file fails to open only when it doesn't parse, isn't this app's format or version, or would crash a reader; its structure is kept by the operations that write it, not checked again. Do not add a repair or defaulting layer that can change meaning.

## Code

- Write the smallest code that does the job. Inline a helper with one caller, keep a small module in its parent, and do not wrap a type without adding a responsibility.
- Reach for a crate before writing code: a well-known external crate first, then one in this repository. Hand-write only what no crate covers, and prefer a cross-platform crate to per-platform branches.
- Keep safe public APIs apart from unsafe FFI, dynamic loading, and build integration.
- Do not hand-edit generated or derived source. Change its input and rerun the generator.
- Comments explain ownership, invariants, upstream mapping, or a deliberate divergence. Do not narrate straightforward code.
- Do not commit credentials, model weights, datasets, generated outputs, or machine-specific files.
- Search with `rg`, never `grep`.

## Interface

- User-visible strings go through the translation function and the locale files. Hardcoded English in a translated surface is incomplete.
- An interface language's display name is that language's own name in every locale.
- The translation-target language list stays in the active UI language. Drop a country name unless the entry is a real variant.
- Do not show status the current selection already implies. Do not add a second job kind, cancel path, or counter for an operation an existing command covers.
- Use the existing control library for standard interaction. Commit on selection or an uncanceled drop, never on focus or hover. Ignore a canceled drag. A shortcut never steals keys from a focused control.

## Models

- A port stays structurally traceable to a commit-pinned upstream implementation. Preserve checkpoint-affecting names, construction order, parameter paths, tensor layouts, execution order, and postprocessing semantics. Explain each intentional divergence next to the affected code.
- Missing or unexpected weights mean an architecture or parameter-name mismatch. Fix that before changing the loader.
- Every model has the same public lifecycle, with model-specific inputs and outputs. Network and weight loading stay apart from preprocessing, postprocessing, slicing, and result types. Do not add pass-through types or layers.
- Accept a device at the model boundary and convert it once. Create token IDs and index tensors on the model device; a CPU tensor used against accelerator embeddings is a defect.
- Use the established loading paths unless they are proven insufficient.
- Disable gradient tracking during inference.

## Performance

- Optimize and benchmark on the actual target device with representative inputs. Load assets and warm models outside the measured region, and account for asynchronous accelerator execution.
- Remove redundant transfers, synchronization, allocations, and per-pixel host loops before adding concurrency or caching.
- Report the device, input size, baseline, result, and correctness difference.

## Verification

- Run the smallest relevant check or focused test once, in the debug profile. Run full suites, other profiles, or end-to-end tests only when asked.
- Add a test only where it protects a real regression boundary. Do not lock a translated phrase, a language display name, a registration string, or a one-line behavior the owner can read. Do not add a second harness for behavior existing tests cover, a test of a compatibility shim, or a benchmark nobody asked for.
- A model port needs a structured comparison with upstream on identical inputs: shapes, ranges, boxes, scores, masks, and ordering. A green build is not that comparison.
- A UI change needs a screenshot of the affected state. For truncation, include a long label.
- A green check is not acceptance.

## Testing

- Automate the UI through a Chrome DevTools Protocol MCP server connected to `http://127.0.0.1:4000`, the debug build's remote debugging endpoint.
- Capture the canvas with the harness's built-in screenshot tool.
- Do not use computer use on Windows.

## Contributing

- A human reviews the whole diff and can explain every change. Do not submit an unreviewed autonomous patch.
- Keep pull-request text short: problem, change, and verification.
- Never add an AI assistant as a commit co-author, for example through a `Co-Authored-By` trailer.
